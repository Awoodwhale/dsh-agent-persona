# 设计决策：v1「一个工作区一个人设」→ v2「多个人设，各自声明适用范围」

- 日期：2026-09-17
- 状态：已实施（存储 `version: 2`，并带自动迁移）

## 背景

v1 的模型是"一个人设挂在一个工作区上，外加一个全局默认"，工作区条目上还有一个 `sessionPrefixes`
字段做补充匹配。用起来立刻暴露两个限制：

1. **人设与工作区被绑成一比一**：同一个工作区想按"渠道"或"会话类型"用不同人设时，表达不出来；
   反过来，一个人设想同时服务多个工作区也要复制多份。
2. **匹配方式单一**：只有"路径相等 + 会话前缀"两种，没法表达"某目录下的所有项目"或"某类会话 id"。

## 决策

把**人设提升为一等实体**，把"应用到哪里"变成人设自己的属性：

```jsonc
{ "id", "name", "enabled", "text",
  "targets": [ { "kind": "workspace" | "sessionId",
                 "match": "exact" | "prefix" | "regex" | "contains",
                 "value": "…" } ] }
```

配套的四条解析规则，目标都是**可解释、可预测**：

| 规则 | 理由 |
|---|---|
| 列表顺序即优先级，第一个命中的生效 | 用户能直接看见并调整（↑↓）；比"最具体者胜"这类隐式规则更好解释 |
| 同一人设内多条规则取「或」 | 一个人设服务多个入口是常态，不该要求复制 |
| 没有规则 = 兜底 | "默认人设"不再是一个特殊字段，而是"没有范围的人设"，概念更少 |
| 停用整体跳过；命中但正文为空 = 显式静默 | 前者是开关，后者让"这里就是不要人设"可以盖住兜底 |

## 被否掉的替代方案

- **多条命中时全部拼接注入**：难预测、难调试（拼接顺序、长度预算、互相矛盾都不可控），
  且与"人设是一段身份"的直觉冲突。保留为将来可能的显式模式。
- **保留 `default` 字段**：与"无范围人设"重复，两套机制并存会让 UI 与解析都更难讲清楚。
- **按工作区建索引**：人设与工作区解耦后，索引不再必要；规则数量是人力规模（几十条），线性扫描足够。

## 迁移

读到 `version !== 2` 的文档时按 v1 语义转换：

- 每个"有正文 / 已启用 / 有 `sessionPrefixes`"的工作区条目 → 一个人设（`workspace 精确 <path>` +
  各前缀转成 `sessionId 前缀`）；
- v1 的 `default`（有内容或启用）→ 一个**无范围**的兜底人设，名字写明来处；
- "停用且正文为空"的条目丢弃，并在告警里点名（它本来也不产生任何注入，语义等价）。

迁移逻辑导出为 `migrateStore`，由 `test/personas.test.mjs` 直接覆盖，包括丢弃报告。

## 影响

- 远程 API 从 5 个变成 8 个（新增 `movePersona` / `duplicatePersona` / `previewMatch`）。
- `previewMatch` 由**宿主**实现：设置页的"命中测试"与真实注入共用同一个解析器，页面不可能与事实漂移。
- UI 从"工作区列表 + 编辑器"改为"人设折叠卡列表 + 内联展开编辑 + 适用范围规则编辑器"。
- 新增人设与副本**一律默认停用**：新增动作永远不改变任何会话当前拿到的人设。
